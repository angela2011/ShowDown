Implemented
- Registration/login with normalized usernames (3–64 ASCII letters/digits/._-) and passwords of 12–128 characters. Username starts with a letter/digit. Passwords are not trimmed or transformed.
- Argon2id hashing using argon2-cffi 25.1.0; 64 MiB memory, 3 iterations, parallelism 1, automatically generated salts. Password work runs off the event loop with at most two concurrent hash operations. Successful login upgrades outdated hash parameters.
- Generic wrong-credential responses, dummy hash verification for unknown usernames, and validation errors that omit submitted input so invalid passwords are not echoed.
- Random 256-bit opaque bearer tokens. Only SHA-256 token digests are stored in the database; tokens are returned once at login. Sessions expire after 8 hours by default; AUTH_SESSION_HOURS supports 1–168. Logout revokes the current token. Deactivated users cannot authenticate or use existing sessions. Responses use Cache-Control: no-store.
- Persistent atomic database-backed fixed-window auth throttles: 10 registrations/hour per peer; login 10 attempts/15 minutes per normalized username and 60/15 minutes per peer. Successful logins count toward quotas. 429 responses include Retry-After. Untrusted X-Forwarded-For headers are not directly read by application code.
- Domain.owner_id references User. Scan ownership is inherited through Scan.domain_id -> Domain.owner_id. Findings, risk scores and results remain JSON within the owned scan; no duplicate ownership columns or new finding tables were needed.
- Every existing domain/verification/scan endpoint requires a valid bearer session. Domain lists filter by owner, and scan detail/history checks enforce that owner before returning raw results or findings. Other users' or unassigned resources return 404. Anonymous/invalid/expired sessions return 401.
- New domain owner is always the authenticated user, never a request-provided owner_id. Existing globally unique domain-name behavior is retained. DNS TXT verification, enqueue rechecks and worker DNS checks remain enforced.
- Worker additionally requires a domain assigned to an active account. Legacy unassigned or disabled-owner jobs fail before DNS/discovery/port scanning.

API (existing gateway prefix /api)
POST /api/auth/register
  JSON: {"username":"your_username","password":"your chosen passphrase"}
  Returns 201 with id and username; does not create a session automatically.
POST /api/auth/login
  Same JSON fields; returns access_token, token_type="bearer", expires_at (UTC).
GET /api/auth/me
POST /api/auth/logout (204)
  Both require Authorization: Bearer <access_token>.

All existing /api/domains/*, /api/verify/* and /api/scans/* operations now require that same Authorization header. Health, registration/login and API documentation remain public. No account hashes, session digests or other users' verification tokens are returned. The unused API_SECRET_KEY setting is not used for bearer validation or token signing; sessions do not depend on its old default value.

Necessary additive migration
New tables: users, auth_sessions, auth_throttles. Added nullable domains.owner_id with foreign key and index. NULL is allowed only to preserve/quarantine legacy rows; API registrations always assign an owner.
The migration is explicit, idempotent and transactional. PostgreSQL uses an advisory transaction lock. It does not rewrite existing domains/scans/results or assign them to the first registered user. API/worker startup detects a legacy domains table without owner_id and refuses to proceed until migration. Fresh database creation remains supported by the API's existing bootstrap behavior.

Operator assignment for existing data
After migration, a registered account can be explicitly assigned a single unowned domain using app.assign_owner. This is a command requiring database/operator access, not an HTTP route. It refuses existing owners, inactive/missing users and domains with queued/running scans. Assignment includes historical results by association, rotates the DNS token and resets verified=False. The owner retrieves the new token through the existing domain endpoint and must verify DNS again. There is no self-service claim or owner-transfer endpoint. Unassigned queued jobs are rejected by the new worker; resolve pending/running jobs before operator assignment.

Remaining limitations and rollout dependencies
- Actual PostgreSQL migration/constraint/concurrent-throttle behavior, trusted-proxy address handling, HTTPS deployment and Azure end-to-end operation remain unverified. SQLite testing does not prove PostgreSQL concurrency semantics.
- The existing frontend is untouched and does not send these tokens. After rollout, its live API calls will receive 401 until a separate login/session integration is implemented. Demo mode is not authentication. No authentication bypass was added for the frontend.
- HTTPS is required for passwords/bearer tokens outside loopback development. The API does not force HTTPS internally because TLS is normally terminated by the gateway. Proxy trust configuration must be validated before rollout; multiple clients may share a peer quota behind a proxy/NAT.
- No MFA, password reset/change flow, email verification, logout-all, user deletion, account-management UI or registration invitation policy is implemented. Registration uses usernames, not email identity.
- Domain names remain globally unique. An unverified registration can reserve a name; contested-domain ownership/expiry/recovery is an operator task. It does not grant DNS verification or access to another owner's data.
- Deactivation rejects future requests/jobs; it does not interrupt an already executing scan. No domain transfer endpoint exists.
- The authorization boundary is the API and worker. Database row-level security is not enabled; direct database operators retain privileged access.
- No historical records were assigned, deleted or exposed. Migration and intended legacy assignments still require execution in the chosen environment.
